# Proofsy — Institutional Cryptographic Signing Architecture

## 1. Executive Summary & Purpose

Proofsy provides educational institutions and event organisers with an **institutional cryptographic signing system** for digital credentials. Every certificate issued through the platform is cryptographically signed using an institution-controlled RSA asymmetric keypair with SHA-256 hashing.

### Key Capabilities
- **Tamper Detection**: Any modification to the certificate claims (e.g. recipient name, event name, issue date) breaks the digital signature.
- **Persistent Key Identity & Versioning**: Keys are versioned (e.g. `inst-rsa-2026-v1`) and persisted, ensuring signatures survive server restarts, worker restarts, and long-term verification years into the future.
- **Key Rotation**: Active keys can be rotated to new versions while keeping past public keys verifiable for older certificates.
- **Provider Decoupling**: Built on the `SigningProvider` abstraction, allowing future integration with CCA-licensed CA (Certifying Authority) DSC or eSign providers without modifying the certificate generation pipeline.
- **Privacy Preservation**: Public verification endpoints display masked recipient identifiers (e.g. `j***e@example.com`) while preserving cryptographic validity.

## 2. Terminology & Compliance Distinctions

| Term | What Proofsy Provides | Important Distinctions |
|---|---|---|
| **Institution Cryptographic Signature** | Yes. An RSA-SHA256 signature generated by the institution's persistent private key identity. | Verifies that the certificate was generated and authorized by the issuing institution without tampering. |
| **Digitally Signed Certificate** | Yes. The certificate PDF and metadata contain an asymmetric digital signature over a canonical payload. | Mathematical guarantee of integrity and authenticity based on public-key cryptography. |
| **QR Code Verification** | Yes. The QR code encodes a public URL pointing to Proofsy's verification service. | The QR code is an access mechanism to the verification service; the mathematical signature provides the tamper-evident proof. |
| **CCA-Issued DSC / eSign** | Not implemented in this version (architecture-ready for future addition). | A CCA-licensed Digital Signature Certificate issued by an Indian Certifying Authority (e.g. eMudhra, Capricorn). Proofsy's `SigningProvider` interface supports plugging this in seamlessly. |

### Core Interface
- `sign(payload, options)`: Returns `{ signature, algorithm, signingKeyId, signingProvider, signedAt, publicKeyPem, fingerprint }`.
- `verify(payload, signature, options)`: Returns `{ isValid, signingKeyId, algorithm, isLegacyPayload, error }`.
- `getActiveKeyId()`: Returns the current active key version (e.g. `inst-rsa-2026-v1`).
- `getPublicKey(keyId)`: Retrieves the public key PEM for the requested key version.
- `rotateKey(newKeyId, options)`: Generates a new active key and marks the current key as retired.
- `listPublicKeys()`: Returns metadata for all known active, previous, and retired keys.

## 4. Canonical Payload Serialization

To prevent hash discrepancies caused by JSON object key reordering, Unicode variations, or date formatting differences, Proofsy enforces **deterministic canonical serialization**.

### Canonical Fields
1. `eventDate`: ISO 8601 UTC string (`YYYY-MM-DDTHH:mm:ss.sssZ`) or `null`
2. `eventName`: Trimmed string, normalized with Unicode NFC
3. `expiresAt`: ISO 8601 UTC string or `null`
4. `issuedAt`: ISO 8601 UTC string
5. `organizationId`: String ID
6. `recipientEmail`: Lowercase, trimmed email
7. `recipientName`: Trimmed string, normalized with Unicode NFC
8. `verificationCode`: Uppercase, trimmed verification code (e.g. `CERT-ABC12345`)

### Serialization Rules
- **Alphabetical Key Sorting**: Keys are sorted in ascending ASCII order.
- **Null Handling**: Explicit `null` representation (never omitted).
- **Encoding**: UTF-8 encoded string passed to `crypto.createSign("SHA256")`.

## 5. Key Management & Rotation

### Directory Structure
```
storage/keys/
├── active_key_id.txt             # Text file containing active key ID (e.g. "inst-rsa-2026-v1")
├── inst-rsa-2026-v1.private.pem  # RSA 2048-bit private key (permissions: 0600)
├── inst-rsa-2026-v1.public.pem   # RSA 2048-bit public key (permissions: 0644)
├── inst-rsa-2026-v1.meta.json    # Metadata (fingerprint, status, createdAt, activatedAt)
├── inst-rsa-2026-v2.private.pem  # Rotated active key
├── inst-rsa-2026-v2.public.pem
└── inst-rsa-2026-v2.meta.json
```

### Rotation Lifecycle
1. **Active**: The current key used for signing all new certificates.
2. **Retired**: A previous key whose private key is no longer used for signing, but whose public key remains active and queryable for historical verification.
3. **Compromised**: A key marked invalid in the event of an operational security incident.

## 7. Disaster Recovery & Key Backup

1. **Production Key Backup**:
   - The `storage/keys/` directory (or cloud key store) must be backed up securely in an encrypted backup vault (e.g. encrypted with GPG / AWS KMS).
   - Never commit private keys to version control (`storage/keys/` is gitignored).
2. **Key Loss Recovery**:
   - If the active private key is lost, new certificates must be issued using a freshly generated key (`inst-rsa-YYYY-vN`).
   - If historical public keys are preserved in `SigningKeyRegistry`, past certificates remain cryptographically verifiable.
